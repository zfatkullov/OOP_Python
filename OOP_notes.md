# Конспект по ООП в Python

## 1. Классы и атрибуты

- **Атрибут класса** общий для всех объектов, **атрибут экземпляра** (`self.x`) свой у каждого.
- **Ловушка:** `items = []` на уровне класса. `a.items.append(1)` виден в `b.items`. Лечение: `self.items = []` в `__init__`.
- **Поиск атрибута:** сначала в объекте, потом в классе, потом в родителях по MRO.
- **`_x`:** договорённость «внутреннее», ничего не блокирует.
- **`__x`:** name mangling, превращается в `_Class__x`. Нужно, чтобы наследник случайно не перезаписал атрибут. Это не настоящая приватность.

## 2. Виды методов

| Вид | Первый аргумент | Зачем |
|---|---|---|
| обычный | `self` (объект) | работа с данными объекта |
| `@classmethod` | `cls` (класс) | альтернативные конструкторы, работа с атрибутами класса |
| `@staticmethod` | ничего | вспомогательная функция, логически связанная с классом |

## 3. `@property`

- Позволяет вызывать геттер/сеттер как обычный атрибут: `obj.x`.
- **Главный плюс:** можно начать с обычного атрибута, позже добавить валидацию, и внешний код не меняется.
- Нет сеттера: атрибут только для чтения (`AttributeError` при записи).

```python
@property
def price(self):
    return self._price

@price.setter
def price(self, v):
    if v < 0:
        raise ValueError("Цена не может быть отрицательной")
    self._price = v
```

## 4. Наследование, `super()`, MRO

- **is-a** → наследование, **has-a** → композиция.
- `super()` идёт **к следующему классу в MRO**, а не просто «к родителю».
- **MRO:** порядок поиска методов, смотреть через `Class.__mro__`. Строится алгоритмом C3: дети раньше родителей, каждый класс один раз.
- **Ромб:** если все классы вызывают `super()`, общий базовый класс отрабатывает один раз.
- **Полиморфизм:** один интерфейс, разные реализации. Функция вызывает `animal.speak()`, не зная, кто это (Dog, Cat).
- **Композиция лучше**, когда нужна гибкость: часть можно заменить (репозиторий подставляется в `Group` снаружи).

## 5. Магические методы

- `__init__` инициализация, `__new__` создание объекта (вызывается раньше).
- `__str__` для пользователя (читаемо), `__repr__` для разработчика (однозначно). Нет `__str__`: `print` берёт `__repr__`.
- `__eq__`, `__lt__` и т.д.: сравнения. `__len__`, `__getitem__`, `__bool__`, `__contains__`.
- `__add__`, `__mul__`: арифметика (`Vector`).
- **Итератор:** `__iter__` (возвращает итератор) и `__next__` (следующий элемент, в конце `StopIteration`).
- **Контекстный менеджер:** `__enter__` и `__exit__` (`Timer`).
- `__call__`: объект вызывается как функция.

### `__eq__` и `__hash__` (частый вопрос)

- Равные объекты **обязаны** иметь равный хеш.
- Определил `__eq__` без `__hash__`: Python ставит `__hash__ = None`, объект нельзя в `set` и ключом `dict`.
- Выходы: написать свой `__hash__` или `@dataclass(frozen=True)`.
- `is` сравнивает identity (тот же объект), `==` сравнивает значения.

## 6. `dataclass`

- Генерирует `__init__`, `__repr__`, `__eq__` (сравнивает все поля по порядку).
- Изменяемое значение по умолчанию: только `field(default_factory=list)`, иначе общий список на всех.
- `__post_init__`: вызывается после `__init__`, сюда ставят валидацию.
- `frozen=True`: поля неизменяемы (`FrozenInstanceError`), хеш генерируется из полей.
- `eq=True` без `frozen`: `__hash__ = None`.
- Аннотации типов Python **не проверяет**, это подсказки.
- Поля со значением по умолчанию идут после полей без значения.

## 7. `__slots__`

- Класс хранит атрибуты в фиксированном наборе, без `__dict__`: меньше памяти, нельзя добавлять новые атрибуты на лету.

## 8. Абстракции: `ABC` и `Protocol`

- **`ABC` + `@abstractmethod`:** наследование явное. Создать объект без реализации всех абстрактных методов нельзя (`TypeError`). Ошибка вылетает сразу при создании, а не позже при вызове.
- **`Protocol`:** структурная типизация (утиная). Наследоваться не нужно, достаточно нужных методов. Проверяет type checker (mypy, IDE), в рантайме ничего не мешает.
- Выбор: нужна жёсткая проверка и общая логика, берём `ABC`. Нужен лёгкий контракт без наследования, берём `Protocol`.

## 9. Паттерны

**Repository.** Прослойка между бизнес-логикой и хранилищем. `Group(title, repo)` ничего не хранит, делегирует. Меняем хранилище (InMemory ↔ FakeDB ↔ файл) без правки `Group`. Все реализации держат одни обещания: `add` дубликат → `ValueError`, `get` нет имени → `KeyError`, `list_all` новый список.

**Factory (простая).** Словарь `{'card': CardProvider}` + функция `create_provider(kind)`. В словаре классы **без скобок**. Это не GoF Factory Method. Минус: новый вид надо дописать в словарь (O не на 100%).

**Singleton.** Один объект на весь процесс, реализация через `__new__`.
- **Ловушка:** `__init__` вызывается при **каждом** `Config()` и сбрасывает состояние.
- Обходы: флаг инициализации в `__init__` или не писать `__init__`.
- В Python проще всего объект на уровне модуля.

## 10. SOLID

- **S (Single Responsibility):** у класса **одна причина для изменения**. Не «одна функция». `Group` считает `best()`, хранение отдано репозиторию.
- **O (Open/Closed):** расширяем **новым классом**, старый код не правим. `shape.area()` лучше, чем `if/elif` по типу.
- **L (Liskov):** наследник выполняет обещания родителя. Если `get` возвращает `None` вместо `KeyError`, ошибка вылетит позже и не там, где причина.
- **I (Interface Segregation):** много маленьких интерфейсов лучше одного большого. Не заставляем класс писать заглушки с `NotImplementedError`.
- **D (Dependency Inversion):** верхний уровень зависит от абстракции, а не от конкретного класса. Зависимость передают снаружи: `Group("A", InMemoryStudentRepository())`.
- **Проверочный вопрос для S:** «кто здесь отвечает за хранение?». `self.repo.add(s)` делегирует (хорошо). `self.students[name] = s` делает сам (нарушает S и D).

## 11. Личные ловушки (перечитать перед собесом)

- Сравнивать **`obj.name`**, а не сам объект. Перед проверкой спросить: «что у меня ключ?».
- `is` против `==`.
- Передавать **объект** (`Repo()`), а не класс (`Repo`).
- Метод вызывать со скобками: `i.total()`, а не `i.total`.
- `dict[key]` бросает `KeyError`, `dict.get(key)` молча возвращает `None`.
- Передавать дальше то, что пришло в параметре, а не жёсткое значение.
- В ответе всегда говорить «**почему**», а не только «да/нет». И называть **тип** исключения.
